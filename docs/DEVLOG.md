# BudGuard / 耳机守护 v2

给 **荣耀手机**用的独立小工具，目标是把华为手机/平板上的**耳机遗落提醒**搬到非华为设备上，
适配 **FreeBuds Pro 3 及更新款**（充电盒带蓝牙信标的那一代，含 FreeBuds Pro 4 / FreeBuds 6 / FreeClip 等）。

---

## 一、官方机制考证（决定了可行性边界）

华为官方说明（[遗落提醒](https://consumer.huawei.com/cn/support/content/zh-cn15977821/)、
[星闪精确查找与离线查找差异](https://consumer.huawei.com/cn/support/content/zh-cn16026148/)）：

| 事实 | 含义 |
|---|---|
| 遗落提醒依赖 **音频管家 16.0.7.321+ / 云空间 15.9.0.300+ / HMS Core** | 华为是靠"系统服务 + 云空间"实现，不是单个 App 自己算 |
| 通知文案"检测到该设备已不在身边，上次记录于XX省XX市XXX附近" | 判定 = 在场/缺席；位置 = 手机自己的定位记录 |
| 离线查找含"播放铃声/导航定位/精确查找/**上线通知**/丢失模式" | 充电盒有独立蓝牙信标，靠"信标消失/上线"驱动 |
| "支持星闪的充电盒同样支持蓝牙，周围设备不支持星闪时通过蓝牙获取位置" | **无星闪的设备（你的平板、荣耀手机）走的是蓝牙那条路** |

结论：**遗落提醒 = 蓝牙信标在场检测 + 手机定位记录 + 系统通知**，其中真正的前置条件是"能看到充电盒的广播"。
云侧那部分（别人帮你找、上报丢失状态）是华为查找网络，**没有第三方 API**。

## 二、实测日志（FreeBuds Pro 3，2026-11-25）

用本 App 的探测页在真实环境抓到的关键两条：

| 广播 | 稳定特征 | 判读 |
|---|---|---|
| `0b 16 ee fd 05 03 00 06 03 87 ff 30`，名字 `HUAWEI FreeBuds Pro 3`，−27 dBm | **Service Data，UUID 0xFDEe，8 字节** | 耳机本体（可连接广播） |
| 厂商数据首字节 `0x20` + 20 字节随机，−39 dBm，**696 次**，单地址长驻 | **Manufacturer Data，类型 0x20，22 字节载荷** | 极可能是**充电盒查找信标**（20 字节轮换密钥） |

同场还有 `WIN-18BTGTTJIBH`（PC，−36 dBm）、Zeekr/Geely 车钥匙、蓝牙秤、NIO 钥匙等 30 多种广播，
说明**"全抓"必然误抓**，必须人工勾选。

由此修掉了两个解析错误：

1. 之前只读 `getServiceUuids()`，而 FreeBuds 用的是 Service Data（AD type 0x16），不在服务 UUID 列表里 → 指纹退化成空，所有同类设备被混成一条。现在改为**自己遍历 AD 结构**。
2. 之前用载荷前两字节猜厂商 ID；现在改用 `SparseArray` 的 **key**（系统已解析好的厂商 ID），并自动兼容"值里是否含厂商 ID"两种实现。

当前指纹格式：`sd:UUID:类型字节:长度` / `mfg:厂商ID:类型字节:长度`，轮换密钥与随机 MAC 都不参与。

## 三、本 App 怎么实现

### A. 连接态遗落提醒（100% 可靠，标准 API）
耳机戴着/连着时监视链路：`ACTION_ACL_DISCONNECTED` 广播 + 每 10s A2DP 状态轮询，
断开后延时确认 → 通知"耳机可能遗落"。适用于走出范围、耳机掉落、摘下放桌上离开。

### B. 收纳态遗落提醒（充电仓内也生效，本版新增）
充电盒不参与 A2DP，只能看它自己的 BLE 广播：

1. **学习**：设置页 →「学习耳机信标」→ 耳机放仓里盖好 → 扫 15s → 勾选 `SD:fdee`（耳机本体）和 `MFG:.../0x20/22B`（充电盒信标）→ 保存。
2. **守护**：后台占空比扫描（扫 12s / 停 40s 省电），这组指纹**全部消失**超过 45s（可调）→ 判定"不在身边"。
3. **防误报**：只有加速度计判定**人确实在走动**（90s 窗口内）才报警；坐着把耳机放桌上不会响。
4. 指纹重新出现 → 自动清除提醒。

> 这套判定和华为的思路一致（信标在场/缺席 + 移动），区别是**全程本地、不联网、不上传**。

### C. 探测日志（关键调试入口）
「学习耳机信标」页会按指纹聚合所有广播并显示：名称、厂商 ID、数据长度、前 3 字节、RSSI、出现次数、原始 hex。
底栏「复制探测日志」= 复制到剪贴板 + 保存到 `Android/data/com.budguard/files/probe/probe-*.txt`。

**这份日志能一次性回答两个问题**：关盖的充电盒到底广不广播、广播指纹长什么样。拿到它就能把识别写死、把误报降到 0。

## 四、HMS 那部分的现实

你要的"通过 HMS 框架发送丢失状态"——**HMS 没有对第三方开放的"查找/丢失状态"接口**。
华为查找网络（Find My Network）只在华为设备与账号体系内流转，公开的 HMS Core 能力是账号、推送、定位、地图、Nearby 等，
没有任何 API 能把设备标记成"丢失"或让别人帮你上报位置。

本版因此把能力做在**本地**（检测 + 通知），这是第三方 App 能拿到的全部。
如果后续要做"云端可见"：

| 方案 | 需要 | 说明 |
|---|---|---|
| 自建后端 + HMS Push Kit 推送 | 华为开发者账号 + agconnect-services.json + 一台服务器 | 延迟 1–2s，数据在你手里 |
| HMS Location/Map Kit 显示最后位置 | 同上 + 地图 Key | 只能显示你自己手机的轨迹，不是众包 |
| 接入华为"查找"网络 | ❌ 无公开接口 | 只有华为自家 App 能做 |

这三条都需要你的开发者账号和签名证书，App 源码里没有硬编码任何账号信息。

## 六、算法设计（自动识别 / 断开判定 / 距离）

### 1. 自动识别（LearnEngine）
学习时对每个 MAC 地址打分，得分高的组连同一并认领：

| 判据 | 分值 |
|---|---|
| 名字含 FreeBuds / FreeClip / HUAWEI / HONOR | +100 |
| 含华为服务数据 `sd:fdee:*` | +60 |
| 含 Apple 厂商数据 `mfg:76:*`（0x004C） | **−200** |
| 名字像车钥匙/门锁/电脑（Zeekr/Geely/NIO/LOCK_/WIN-） | −120 |
| 最强 RSSI ≥ −45 / −55 / −65 | +30 / +18 / +8 |
| 出现次数 ≥ 20 | +10 |

认领规则：名字命中无条件认领；其余要求「得分 ≥ 40 且最强 RSSI 在 top−15dB 内」——把隔壁同事的同款耳机排除。Apple 一律不认领。

**用真实日志验算**（`work/apk_analyze/learn_sim.py`）：
`BC:7F…`（200 分，HUAWEI FreeBuds Pro 3）+ `C6:9E…`（100 分，同强、另一帧型）被认领；
Apple 四条（−200）、门锁 LOCK_d3e4（−130）全部排除。

### 2. 距离模型（SignalModel）
- **中位数滤波**（5 窗）而非 EMA：人转身遮挡产生的 −20dB 尖峰不会引发误判。
- **在线噪声估计**：跟踪中位数相邻两次的绝对差，得到这台设备在你环境里的真实抖动 σ（下限 1.5dB）。
- 对数路径损耗 `d = 10^((A−RSSI)/20)`，A 在学习时按「盒距手机 0.3m」标定为 `A = 中位RSSI − 10.5`。
- 门限判定按档位留不同裕量（越近越卡紧），并**持续 6 秒**才报，抑制瞬时抖动。

### 2.1 四档触发距离

| 档位 | 名义距离 | 距离判定 | 噪声裕量 | 用你的日志（A=−37.5, σ≈3）估算的实际触发距离 |
|---|---|---|---|---|
| 形影不离 | < 1 m | 是 | 0.2σ | **≈1.1 m** |
| 随身携带 | 2 m | 是 | 0.4σ | **≈2.3 m** |
| 待在附近 | 5 m | 是 | 0.5σ | **≈5.9 m** |
| 完全断开 | — | **否** | — | 只在收不到广播（静默 45s）时判定 |

第 4 档关掉距离层，只保留"消失层"，语义就是你说的"无法扫描到信号"才提醒。

### 3. 断开/遗落判定（三级）
1. **链路层**：`ACTION_ACL_DISCONNECTED` 广播 + 每 10s A2DP 状态轮询，断开后按 0–30s 防抖延时确认。
2. **距离层**：还能收到信标时，若按模型已明显超出「遗落距离」并持续 10s → 提前报警（不用等信号彻底消失）。
3. **消失层**：信标静默超过 `absenceSec`（默认 45s）→ 判定不在身边。

三层都要求**加速度计确认人在走动**（90s 窗口），坐着把耳机放桌上不会响。任一层的报警在信标回到范围后自动撤销。

### 4. 扫描策略（本轮调整）

**扫 15 秒 / 停 20 秒**（固定占空比），判定每 8 秒一轮。

- 每轮 `onScan` 打开 15 秒扫描，`offScan` 停 20 秒，循环往复；判定时钟独立跑，不随扫描开停变化。
- 扫描模式 `SCAN_MODE_BALANCED`：窗口内采样足够密，RSSI 距离估算稳定。
- 扫描存活自愈：若蓝牙被关过，下一轮 `onScan` 会自动重新启动。


## 七、部件级提醒（左耳 / 右耳 / 充电仓）

一次耳机系统会以**多个 BLE 地址**出现。程序按「部件」建模：

```
部件 = 地址 + 角色 + 该部件的指纹集合
```

学习完自动识别后，会逐个弹窗让你点一下角色（左耳 / 右耳 / 充电仓 / 耳机整体 / 忽略）。默认猜测是：**带产品名的通常是充电仓**（仓里有独立 BLE 芯片负责离线查找），其余按出现顺序给左右耳——猜错可以在弹窗里改。

提醒文案按下表生成（完全覆盖你列的七种）：

| 缺失部件 | 文案 |
|---|---|
| 左耳 | 左耳遗落 |
| 右耳 | 右耳遗落 |
| 仓 | 耳机仓遗落 |
| 左耳+仓 | 左耳+耳机仓遗落 |
| 右耳+仓 | 右耳+耳机仓遗落 |
| 左耳+右耳 | 左耳+右耳遗落 |
| 三者 | 左耳+右耳+耳机仓遗落 |
| 无法区分（只学了一个整体） | 耳机遗落 |

**必须知道的物理边界**：耳机放回仓里会关机、停止广播，此时只剩仓在喊。
所以「耳机在仓里被落下」只能报 **耳机仓遗落**（等价于整副）；**左耳/右耳遗落只在你把某一只取出后才有独立广播可判**。这不是实现问题，是耳机断电后没有任何信号。
程序每个部件单独计时、单独算距离，组合变化时会重新提醒一次（例如先丢右耳、再丢了仓）。

## 八、灵敏度（本轮调整）

| 参数 | 旧 | 新 |
|---|---|---|
| 判定轮询 | 15 s | **8 s** |
| 超距需持续 | 10 s | **6 s** |
| 距离门限裕量 | 1.0σ | **0.5σ** |

## 九、后台通知（本轮调整）

前台常驻通知不再显示"正在连接/已连接/未连接"，统一为：

> 守护中：耳机 — 后台近场守护中（低功耗扫描，不需要保持连接）

因为现在的判定完全靠广播，与是否保持蓝牙连接无关，显示连接状态会误导。



## 十、已知边界

1. **仓内已由实测确认**：`sd:fdee:01:11`（flags=0x00 不可连接、−25dBm、159 次）在关盖状态下持续广播，说明充电盒一直在喊。上一份日志里的 `mfg:…/0x20/22B` 这次消失，判定为临时帧，已不再依赖它。
2. 指纹是**设备型号级**而非个体级（轮换密钥无法在无密钥前提下区分"我的"与"别人的同款"）。独处场景准确；人多场景可能把别人的同款当成"在场"（宁可不报，不误报）。
3. 距离标定假设「学习时盒距手机约 0.3m」；若你把它贴在手机上学习，所有距离会被高估约 3 倍，**建议按界面提示放到 30cm 左右再点识别**。
4. 左右耳/仓的角色是**学习时你标的**，程序不会去读华为私有协议（第三方拿不到）。标错可在重新学习时改。
5. 首次使用必须走一遍学习流程；换耳机/换仓需重新学习。
6. 未做真机验证（构建环境无 adb/模拟器）。上机后请先确认三件事：关盖静置时是否稳定"在场"、走开 5 米是否在 6 秒内触发、坐着不动是否不误报。

## 十一、逆向 AndPods 的结论（本轮）

目标包：`cn.xiaolongonly.andpodsop` v4.4.1（AndPods，31.7 MB，SHA-256 `C7F1F425…AAC0E7`）。

| 取证项 | 结果 |
|---|---|
| Manifest | minSdk 21 / targetSdk 35，蓝牙扫描+连接权限齐全 |
| 华为解析器 | `cn.xiaolongonly.andpodsop.parser.HUAWEIFreeBudsParser implements BaseParser` |
| 关键方法 | `dataCreator(byte[], long, HeadsetDataConfig)`、`dataUpdate(...)` —— **access = PUBLIC NATIVE**，Java 层是空壳 |
| native 库 | `libjutils.so` 内查不到 JNI 符号、`dataCreator`、`HUAWEI`、`FreeBuds` 字符串 |
| 加固 | `libshell-superv.2019.so` / `libshell-supervbasic.2019.so` → 腾讯乐固 VMP，native 代码被虚拟化保护 |

**结论：静态逆向拿不到字节布局。** 真正解析在乐固保护的 native 里，符号与字符串不可见；要提取只能 Frida 动态 hook（需 root 与脱壳），这份 APK 的 Java 层不含任何解析逻辑。

### 找到的公开协议资料

[HyperEars 的华为 FreeBuds 协议记录](https://github.com/silverpoetry/HyperEars/blob/main/docs/huawei-freebuds-protocol.md)（基于 OpenFreebuds 交叉验证）给出连接态协议：

```
帧: 5A <len:2BE> 00 <cmd:2> <TLV...> <crc16/XMODEM>
电量: 01 08（查询）/ 01 27（主动上报）
      → 参数1 = 整机%，参数2 = [左, 右, 仓]，参数3 = 充电标志
```

**关键：参数 2 中的 `0` 表示该部件未连接（单耳佩戴或不在盒内）。**

也就是说，华为手机知道左右耳/仓在不在，靠的是**连接后经 RFCOMM SPP 主动上报**（Pro 3 用 channel 1，5i 用 channel 16），不是 BLE 广播——BLE 广播里没有等价的公开字段。

### 因此采用的方案：引导式自动校准

既然字段拿不到，就用**物理动作**让程序自己确定角色，不猜、不依赖私有字节：

| 步骤 | 你的动作 | 程序得到的结论 |
|---|---|---|
| 1 | 两只耳机都放仓、**盖好** | 先**只做识别**：过滤掉 Apple 设备 / 车钥匙 / 门锁等噪声，把仍在广播的华为信号识别为**充电仓**，结果只展示、不写设置 |
| 2 | 只取出左耳 | 这一步新出现的华为信号 = **左耳** |
| 3 | 左耳放回、只取右耳 | 这一步新出现的华为信号 = **右耳** |

每步扫 15 秒，第 1 步结束会显示「识别到 N 个属于你的信号（含充电仓地址与 RSSI）」，确认后再进入取放步骤。角色由动作唯一确定，**全程没有任何逐条点选**。

### 已移除：SPP 读取

按需求删除了连接态 SPP 功能（`SppActivity` / `HuaweiSpp` / 入口按钮）。原因记录在此以备将来：实测表明 SPP 能连通、CRC 校验通过，但读请求必须携带零长度 TLV 参数清单（`01 00 02 00 03 00`），且该通道只在耳机取出/连接时可用，仓内断电不可用——与"仓内遗落"主场景不匹配，故不作为产品功能保留。




## 十二、常驻通知显示遗落状态（本轮）

前台常驻通知不再是静态文案，而是直接反映检测状态：

| 状态 | 通知内容 |
|---|---|
| 未开启收纳态守护 | 耳机守护 · 耳机 — 后台守护中 |
| 守护中且有信号 | 耳机守护 · **耳机 — 在附近** |
| 判定遗落 | 耳机守护 · **耳机 — 遗落** |

状态由遗落判定直接驱动：checkAbsence() 一旦把某个部件纳入缺失集合就把 leftBehind 置真并刷新通知；部件重新被听到（或缺失集合清空）立刻回到「在附近」并撤掉提醒通知。

### 通知标题用配对型号（本轮）

常驻通知里的「耳机」已替换为实际型号，取值优先级：

1. 校准过程中从广播读到的产品名（`sd:fdee` 帧的 Complete Local Name，如 `HUAWEI FreeBuds Pro 3`）；
2. 主页「选择耳机」时保存的蓝牙设备名；
3. 系统蓝牙栈里该地址的 `getName()`；
4. 都没有时退回「耳机」。

最终形态：

```
HUAWEI FreeBuds Pro 3
在附近                      ← 或「遗落」/「后台守护中」
```

校准保存时会把型号写进 Profile 的 `deviceName`，重新校准后通知标题会自动更新。

## 十三、「耳机是否在仓内」确认（本轮）

充电仓在附近、而左右耳都没广播时，分不清是「在仓里」还是「掉在别处」。这时不直接报警，先问一次：

```
充电仓在附近 + 左右耳都静默
        │
        ├─ 询问（通知按钮 + 主页卡片）
        │     ├─ 「在仓内」→ 进入仓内态：不报左耳/右耳遗落，只守充电仓
        │     ├─ 「不在仓」 → 立刻按正常流程报警
        │     └─ 90 秒无响应 → 按「不在仓」处理，照常报警
        │
        └─ 仓内态下：左/右耳重新广播或重新连接（被取出用过）→ 确认作废
                     再次放回、左右耳又静默 → 重新询问一次
```

- 询问入口有两处：**通知上的两个按钮**（锁屏也能点）和 **主页的确认卡片**（打开 App 自动出现）。
- 常驻通知在三种状态下分别显示：`在附近` / `待确认：耳机是否在仓内` / `在仓内（只守充电仓）`。
- 「本轮已问过」标记保证同一轮不会反复弹；一轮结束（部件全部回来）后自动复位。
- 仓内态下如果**充电仓本身**消失，仍然照常报「耳机仓遗落」。

## 十四、提醒节奏（本轮）

### 1. 样本新鲜度门槛

距离判定必须同时满足：

```java
boolean fresh = scanning && m.hasData() && (now - m.lastSampleAt()) <= 10_000;
```

- 只有**扫描窗口开着**时才判距离；
- 只认**最近 10 秒内**的新样本。

因此 20 秒停顿期不会拿旧 RSSI 下结论；「超出距离持续 6 秒」必须完整落在 15 秒扫描窗口内才触发。

### 2. 2 分钟冷却

`ALERT_COOLDOWN_MS = 120_000`：同一场景下**最多每 2 分钟提醒一次**。

- 首次超出范围：立即提醒；
- 之后仍在外：状态照常更新（通知继续显示「遗落」），但**不再重复弹通知**；
- 但回到范围内（missing 清空）：`lastAlertAt` 归零，下一次遗落**立刻**提醒，不用等冷却；
- 冷却只作用于「距离/存在性」这类遗落提醒，不影响「耳机是否在仓内」的确认询问。

## 十五、两个 Bug 修复 + 距离显示（本轮）

### Bug 1：回到范围后状态栏不更新

**根因**：常驻通知只在「状态发生变化的某几个分支」里刷新（`onBeaconSeen` 里还有 `alertedKey == null` 就提前 return 的短路），一旦某条路径没走到刷新，通知就停在「遗落」。

**修法**：
- `presenceTick` 每 8 秒**无条件**调一次 `updateOngoing()`，保证状态栏最多滞后一轮；
- `onBeaconSeen()` 的短路条件改成 `alertedKey == null && !leftBehind`，遗落中扫到信标也会立刻刷新。

### Bug 2：耳机重新上线后「最后在线」不更新

**根因**：界面读的是设备列表里的 `lastSeen`，而这个字段**只在选择设备时写入一次**；后台每次听到广播并没有回写。

**修法**：
- `Store` 新增实时字段 `last_seen_at` / `last_dist`；
- 服务每 2 秒限频回写一次（`store.setLastDistance`），链路连上时也 `touchSeen`；
- 界面「最后在线」改为优先读这个实时字段。

### 新增：距离显示

**通知栏**（常驻，每 8 秒刷新）：

```
HUAWEI FreeBuds Pro 3
在附近 · 约 0.8 米          /  遗落 · 约 6.2 米          /  遗落 · 信号已断开
```

**应用内**（状态行，每 2 秒刷新）：

```
状态：在附近
距离：约 0.8 米 · 最后在线：刚刚
```

超过 20 秒没有新样本时，距离一律显示「信号已断开」，避免显示过期读数。

## 十六、遗落记录：时间 / 距离 / 位置

### 记录什么

每条遗落记录包含：时间、判定时的距离、**推定位置**、**判定时刻位置**、中文地址、可信度。

### 落点怎么定（拟合规则）

耳机自己不会说话，真正有信息量的是"你最后一次离它很近时手机在哪"：

1. 后台每收到一次广播就更新距离；当距离 **≤ 2 米**时，把当时的定位存为 `lastNear`；
2. 判定遗落时取 `lastNear` 作为**推定位置**（最接近耳机实际落点）；
3. 同时取当前定位作为**判定时刻位置**（人已走开几米，仅作辅助）；
4. 两者都有效时按 `1/acc²` 加权融合，且 `lastNear` 权重 ×2（先验更可信）；
5. 可信度：无 `lastNear` 扣 30 分，精度 >20m / >50m / >100m 分别再扣。

### 定位准确性措施

| 措施 | 说明 |
|---|---|
| 双 Provider | GPS + 网络定位同时注册，取可用者 |
| 60 秒采样 | `requestLocationUpdates(60s, 20m)`，静止时也会补一次 `getLastKnownLocation` |
| 前台服务类型 | `foregroundServiceType="connectedDevice|location"`，服务在跑即可后台采样，**不需要"始终允许位置"权限** |
| 精度标注 | 每条记录都带精度半径，界面标明"好/一般/差" |

### 中文地址

用系统 `Geocoder`（`Geocoder.isPresent()` 为假时跳过）在后台线程解析，解析成功后回写记录。
**如果设备没有可用的地理编码后端，地址会留空、界面显示经纬度**——这一点由系统决定，App 不做假数据。

### 历史与清理

- 最多 **10 条**，只保留 **48 小时**内（读取时自动过滤过期）；
- 耳机**回到身边**后，通知栏 + 主页都会问一次"要清除遗落记录吗？"（清除 / 保留）；
- 记录页可逐条查看详情，并支持"在地图上打开"（`geo:` 意图）。

## 十七、答问倒推 + 20 秒定位 + 文案统一（本轮）

### 1. 「不在仓」时按答问耗时倒推位置

时间线：

```
T0  弹出「耳机是否在仓内？」
T0+12s  你点了「不在仓」
```

- 记录时间取 **T0**（提问时刻，更接近真正遗落的时刻）；
- 记录位置取 **≤T0 的最近一次定位**（`LocTracker.lastBefore(T0)`），把"你看通知、想了一下、再点按钮"这十几秒的走动排除掉；
- 「在仓内」不落记录，所以不受影响。

### 2. 实时定位改为 20 秒一次

`LocTracker`：`requestLocationUpdates(20s, 0m)`，GPS + 网络双 Provider。
采样越密，倒推时的误差上限越小（最多早 20 秒）。代价是耗电明显高于 60 秒。

### 3. 状态栏文案与提醒文案统一

| 场景 | 常驻通知 | 提醒通知 |
|---|---|---|
| 在附近 | `在附近 · 约 0.8 米` | — |
| 遗落 | `左耳+右耳遗落 · 约 6.2 米` | 标题 `左耳+右耳遗落`，正文 `约 6.2 米 · 点此查看` |
| 信号断了 | `左耳+右耳遗落 · 信号已断开` | 标题同上，正文 `信号已断开 · 点此查看` |
| 刚启动 | `在附近 · 等待信号` | — |

判定文案（`左耳遗落 / 右耳遗落 / 耳机仓遗落 / 左耳+右耳遗落 / 左耳+耳机仓遗落 …`）
由同一个 `Profile.missingText()` 生成，状态栏与提醒不会再出现两套说法。
